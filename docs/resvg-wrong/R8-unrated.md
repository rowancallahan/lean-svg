# R8-unrated — the 61 files resvg's own `results.csv` does not rate

## Why this file exists

For all 61 files below, `tests/corpora/resvg-test-suite/results.csv` rates
**no renderer at all** — every column (chrome, firefox, safari, resvg,
batik, inkscape, librsvg, svgnet, qtsvg) is `0` (untested). This is not a
gap in the CSV: every one of these 61 files carries `(UB)` in its `<title>`
(or, for the five `shapes/rect/*-values.svg` CSS-unit files, `(SVG 2)`), and
the suite's own tooling (`site/gen-html-tables.py`: `if "(UB)" in
row.title: continue`; `stats.py`'s `# Skip UB`) deliberately excludes
`(UB)`-titled rows from scoring. So `results.csv` isn't silent by omission —
the suite's maintainers already decided these rows have no single
agreed-correct answer worth scoring.

A second, load-bearing finding, true across every batch below: **most of
these files' own `suite.png` reference is not a rendered scene at all** — it
is a generic placeholder graphic that literally reads "UB". Where a real
suite reference PNG *does* exist (the `shapes/rect/*-values.svg` files, and
`painting/stroke-width/negative.svg`), it appears to have been generated by
resvg itself (or a resvg-family tool) rather than an independent renderer —
it always agrees with resvg's own (sometimes spec-incomplete) behavior, never
independently corroborates or contradicts it. That matters for the
shallow-fix gate below.

## Method

Per file: render four ways at 200px wide (ours, resvg 0.48.1, the suite's own
PNG resized to 200 wide, and headless Chromium), read the SVG's own
title/comments/structure, check the relevant spec text, check our own
implementation, and — where useful — resvg's GitHub source/issues at tag
v0.48.1. Six research passes (one per file cluster) did this work in
parallel; this document stitches their findings together, verifies the two
strongest shallow-fix candidates they proposed against the task's own
evidence bar, and reclassifies where that bar isn't met.

**On the auto-fix gate.** The task allows a class-(a) shallow fix to be
committed directly only "when the suite PNG and Chromium agree with each
other and with the spec." Applying that literally and checking it for every
candidate (not just trusting a classification) turned out to matter: across
all 61 files, **zero meet that bar**. The clearest near-misses
(`shapes/rect/ic-values.svg`, `shapes/rect/vi-and-vb-values.svg`) have a
small, well-understood fix and a real gap vs. Chrome/spec, but their own
suite reference PNG sides with resvg's gap, not with Chrome — so the gate
explicitly built into this task to avoid unreviewed fidelity regressions
against resvg says "no" for both. Consequently: **this document makes no
code changes.** Everything below is analysis and classification for later,
reviewed decisions.

## Per-file findings

### `filters/enable-background/with-mask.svg`

**What it tests.** `enable-background="new"` + a `<filter>` on an empty `<g id="g3">`
whose sole primitive is `<feOffset in="BackgroundImage" dx="100"/>`. `enable-background`
and `BackgroundImage`/`BackgroundAlpha` filter inputs were dropped from SVG 2 and no
modern renderer implements them; resvg's usvg parser prints
`Warning: BackgroundImage filter input isn't supported and not planed` and falls back
to treating the input as `SourceGraphic`.

**Renders.** `ours.png`, `resvg.png` and `chrome.png` are pixel-identical: a green
square (`rect2`), overlapped by a rect (`rect3`) masked by a gradient mask so it fades
from transparent to blue, and no visible trace of `g3`/the filter at all. `suite.png`
is the suite's "UB" placeholder card, not an actual reference.

**Correct output + confidence: high.** Since `g3` is a bare empty `<g>`
(`<g id="g3" filter="url(#filter1)"/>`, no children), its `SourceGraphic` is fully
transparent no matter how `BackgroundImage` is resolved — offsetting transparent pixels
still gives transparent pixels. So this file cannot actually discriminate a
`BackgroundImage`-aware implementation from a `BackgroundImage`-as-`SourceGraphic`
fallback; all three renderers agreeing is expected and not strong evidence either way,
but it does confirm nothing crashes or misbehaves.

**resvg verdict:** resvg correct (matches its own documented, deliberate non-support).

**Classification: (c)** deliberately not supported. `BackgroundImage`/`BackgroundAlpha`
require rendering everything *behind* the filtered element into an offscreen buffer at
filter time — a form of non-local state that doesn't fit this renderer's per-element,
single-pass model (DESIGN.md §3: `groupBegin`/`groupEnd` process one subtree at a
time, nothing looks at siblings-so-far). resvg itself declined to implement it
("not planed" is upstream's own wording), and mirroring resvg's fallback (treat as
`SourceGraphic`) is exactly what `LeanSvg/Filter.lean:548` already does.

**Our status.** `LeanSvg/Filter.lean`, `resolveInput` (line 542-557): `BackgroundImage`
and `BackgroundAlpha` (along with `FillPaint`/`StrokePaint`, see the FillPaint file in
a sibling batch) are matched at line 548 and mapped to `.source`, i.e. treated as
`SourceGraphic` — the same fallback resvg's usvg takes. No fix needed.

### `filters/feColorMatrix/type=saturate-with-a-large-coefficient.svg`

**What it tests.** `feColorMatrix type="saturate" values="99999"` — the spec's
"a single real number value (0 to 1)" restricted range, fed a wildly out-of-range
value. Filter-effects-1 doesn't define behavior outside 0..1, hence "(UB)".

**Renders.** `ours.png` and `resvg.png` are visually identical: a **muted, close to
the original-looking** vertical gradient (magenta → dark green → dark maroon → pale
blue-violet), *not* a hyper-saturated result. `chrome.png` instead shows extremely
vivid, fully-saturated bands (bright magenta / bright green / red / magenta / blue) —
Chromium clearly applies the huge coefficient literally and clamps hard per-channel.
`suite.png` is the "UB" card.

**Correct output + confidence: high (for "matches our stated target"), n/a (for
"the one true spec answer" — there isn't one).** resvg's `color_matrix.rs::saturate`
builds the classic Rec.601 saturation 3×3 with the raw (unclamped-above) coefficient,
computed in `f32`, and then truncates to `u8` (`as u8`, which truncates toward zero
rather than rounding and wraps/clamps oddly for huge intermediate floats) — this is
exactly what produces the muted-not-vivid look in both `ours.png` and `resvg.png`. Both are internally
consistent with resvg's own arithmetic; Chromium's math differs (likely rounds/clamps
per-channel through a different code path, e.g. `Skia`'s color matrix filter, which
doesn't reproduce resvg's `f32`-then-truncating-cast sequence).

**resvg verdict:** cannot tell against "the spec" (there's no defined answer for
values > 1), but ours matches resvg's chosen (also UB-but-consistent) interpretation
exactly.

**Classification:** effectively no fix needed; closest bucket is **(c)** — the project
deliberately implements resvg's specific arithmetic (`f32` binary32 math, truncating
`as u8` cast) rather than "the mathematically most sensible clamp", because pixel
fidelity to resvg 0.48.1 is the explicit target (DESIGN.md §1/§3.11), and it succeeds
here.

**Our status.** `LeanSvg/FilterApply.lean`: `sat3` (line 213-220) builds the 3×3 from
the raw coefficient (`v`) with no upper clamp; `colorMatrix`'s `.saturate` case
(line 254-256) only clamps *negative* values to 0 (`if F32.isNeg v then 0 else v`),
leaving arbitrarily large values unclamped, same as resvg. The final per-channel
result goes through `f32TruncU8` (truncating cast, matching Rust's `as u8`). This
already matches resvg bit-for-bit in the render (max channel diff 1).

### `filters/feColorMatrix/type=saturate-with-negative-coefficient.svg`

**What it tests.** Same primitive with `values="-0.5"`, i.e. a negative saturation
coefficient — also outside the defined 0..1 range.

**Renders.** `ours.png`/`resvg.png` are identical: a **fully desaturated (grayscale)**
vertical gradient — consistent with the negative value being clamped to 0 before
building the 3×3 (saturate=0 is exactly the standard luminance/grayscale matrix).
`chrome.png` instead shows a colorful, partially-inverted-looking gradient (green /
mauve / dark teal / khaki) — evidence Chromium does *not* clamp negative saturate to 0
and instead applies the negative coefficient literally, producing an "anti-saturated"
(complementary-leaning) result.

**Correct output + confidence: high (relative to resvg target).** `sat3 (if
F32.isNeg v then 0 else v)` (FilterApply.lean:256) explicitly clamps negative to 0
before building the matrix, mirroring resvg's own `saturate` clamp
(`crates/usvg/src/parser/filter.rs` / `resvg`'s `color_matrix.rs` clamps the value to
`0.0..=1.0` on the *lower* end at minimum for `saturate`; the upstream source and our
port agree, hence the pixel-identical renders).

**resvg verdict:** cannot tell against a universal spec answer, but matches resvg's
choice.

**Classification: (c)**, same reasoning as the previous file — deliberately following
resvg's own (also-UB, but fixed and documented in its source) clamp behavior rather
than Chromium's.

**Our status.** Same code path as above (`FilterApply.lean` `sat3`/`colorMatrix`);
already correct, no fix needed.

### `filters/feConvolveMatrix/bias=-0.5.svg`

**What it tests.** `feConvolveMatrix` with a 3×3 box-blur-ish kernel (`0.1` × 9,
divisor defaults to kernel sum = 0.9) and `bias="-0.5"`, applied to a blue/yellow
checker pattern. Per filter-effects-1 §15.10, the color-channel formula is
`RESULT = (Σ kernel·source)/divisor + bias·ALPHA_result`, and the *alpha* channel
formula is `ALPHA_result = (Σ kernel·source_alpha)/divisor + bias` (bias added
directly, not scaled by alpha). A negative bias here should darken/reduce alpha
outside the defined 0..1 UB territory (bias isn't restricted by spec, but combined
with input that has zero-alpha regions it produces edge cases the suite calls UB —
likely for how it interacts with premultiplied-alpha clamping).

**Renders.** `ours.png` and `resvg.png` are pixel-identical: blue/yellow checker
squares on a plain **white** background (i.e. the -0.5 bias drives already-low alpha
further negative, clamps to 0, so the background stays fully transparent/white).
`chrome.png` shows the same squares but each square has a visible darker gray-olive
halo/overlap tint not present in ours/resvg — Chromium's compositing of the bias
effect at square boundaries differs slightly, likely due to a different premultiplied-
vs-straight-alpha bias order or a different divisor/rounding path.

**Correct output + confidence: medium-high.** The overall structure (checker pattern
faithfully reproduced, background unaffected because -0.5 bias only pushes alpha
further toward 0, which clamps) matches the expected sign behavior. Ours matches
resvg exactly, which is the stated target; Chromium's divergence at the edges is
plausibly its own rounding/compositing order, not obviously "more correct" by the
spec text.

**resvg verdict:** cannot tell definitively (no browser consensus point exists among
the 4 tested renderers per the CSV; here we only have Chromium to compare and it
disagrees at the margins) — but matches resvg exactly.

**Classification: (c)** — matches resvg's specific bias/premultiplication order
(`LeanSvg/Filter/ConvolveMatrix.lean` ports resvg's `convolve_matrix.rs` directly per
its own file header), no fix needed for our fidelity target.

**Our status.** `LeanSvg/Filter/ConvolveMatrix.lean::run` (lines ~54-100): computes the
alpha result as `F32.add (F32.div newA divisor) bias` (bias added straight to alpha,
per spec) and the color result as `F32.add (F32.div v divisor) (F32.mul bias finalA)`
(bias scaled by the *result* alpha, per spec) — this is a correct, literal
transcription of filter-effects-1 §15.10's two different bias formulas, and matches
resvg's implementation bit for bit here.

### `filters/feConvolveMatrix/bias=0.5.svg`

**What it tests.** Same as above with `bias="0.5"` (positive) — this time bias should
*raise* alpha, including in regions where the source was fully transparent.

**Renders.** `ours.png`/`resvg.png` are identical: the same checker squares, but now
sitting on a **light gray, semi-transparent haze covering the whole filter region**
(background pixels get alpha ≈ 0.5×255 from the `+bias` alpha term even though their
convolved source alpha was 0, composited over white → light gray). `chrome.png` shows
the squares on a plain **white** background with no haze at all — Chromium is not
applying the alpha bias term to originally-fully-transparent pixels, or its filter
region/optimization skips regions it considers "empty" before the bias is applied.

**Correct output + confidence: high, in favor of ours/resvg.** filter-effects-1
§15.10's alpha formula is `ALPHA_result = (Σ...)/divisor + bias`, unconditionally —
there is no "only if source pixel was non-transparent" carve-out. A literal spec
reading says the gray haze *should* appear over the whole filter subregion, i.e.
ours/resvg's rendering is the more spec-faithful one, and Chromium is arguably the
outlier here (possibly an optimization that treats transparent-black regions as
already converged and skips per-pixel filter math, a known category of shortcut in
compositor-based filter pipelines).

**resvg verdict:** resvg correct (spec-literal), and ours matches it exactly.

**Classification: (c)** — no fix needed; already matches both resvg and (arguably) the
literal spec text better than Chromium does.

**Our status.** Same `ConvolveMatrix.lean::run` as above; the unconditional `+ bias`
on alpha (not gated on source alpha) is exactly why the whole canvas gets the haze.
Confirmed correct.

**Our status.** `LeanSvg/Filter/ConvolveMatrix.lean::run`'s `edgeMode=wrap` index

### `filters/feTile/complex-transform.svg`

**What it tests.** `feFlood` (a small 10×10 green square at a fixed filter-region
position) → `feOffset(5,5)` → `feTile`, applied to a `<rect>` that itself has
`transform="skewX(30) rotate(30)"` — i.e. a **non-similarity (skew) transform** on the
filtered element. The suite's own naming ("complex-transform") plus "(UB)" flags this
as specifically probing how implementations handle filters under transforms that
aren't just translate/scale/pure-rotate.

**Renders.** `ours.png` and `resvg.png` are pixel-identical: an axis-aligned grid of
small green tile-repeat stripes, filling an axis-aligned square — the tiling and the
whole filter computation happen in an *un-skewed* coordinate frame, and only the
overall image ends up flat/axis-aligned (i.e., the skew is effectively dropped from
the filter's internal geometry). `chrome.png` shows the *same* stripe pattern but
visibly **skewed/rotated** to follow the element's actual `skewX(30) rotate(30)`
transform, exactly as a literal reading of "filters operate in the local coordinate
system established by the element's transform" would predict.

**Correct output + confidence: medium (resvg-target), low (spec-ideal).** This is a
genuine, known, and already-documented divergence from a naive/idealized spec reading:
resvg computes filters in a filter-region-aligned bitmap using an approximated
(axis-aligned) transform rather than truly arbitrary 2D affine transforms, so skew
components are lost. Chromium's output looks more "correct" against filter-effects-1's
coordinate-system text. But **ours was explicitly built and unit-tested against this
exact file to match resvg's specific (arguably non-spec-ideal) behavior** — see the
code comment cited below, which names this file directly and documents the
intersect-vs-contain nuance in resvg's own `Pixmap::clone_rect`.

**resvg verdict:** resvg wrong relative to an idealized "should follow arbitrary
transforms" spec reading, but this is a known/deliberate resvg architectural
limitation (filters computed on an axis-aligned device-pixel raster), not a bug in
our port of it. Ours matches resvg's (wrong-relative-to-Chromium) behavior exactly by
design.

**Classification: (c)** deliberately matches resvg's own limitation. Making our tile
geometry follow arbitrary (skew) transforms would require abandoning the
axis-aligned-filter-canvas architecture described in DESIGN.md §3.11 ("A filter layer
is a coordinate frame of its own... that shift is a whole number of pixels, so
coverage is unchanged") for full affine resampling — a large architectural change,
and one that would move us *away* from resvg fidelity (our stated goal), not toward
it, since resvg has the same limitation. Not something to fix unless the project's
target shifts from "match resvg" to "match the spec ideal / match Chromium".

**Our status.** `LeanSvg/Filter/Tile.lean` (top-of-file doc comment, lines 3-24)
explicitly says this file was checked against resvg 0.48.1 by name: *"Checked against
`resvg` 0.48.1 on `feTile/simple-case`... and `feTile/complex-transform`... both come
back with only `{0, 255}` alpha"* — i.e. the author already ran this exact file
against upstream resvg and hand-verified the match. `runTileCanvas` (lines 42+) also
has a paragraph (lines 29-41) specifically about this file's `feFlood` sub-region
"poking outside the filter region under a skew," citing the file by name and
explaining it's `to_int_rect` rounding, not a geometric bug. This is about as
thoroughly pre-analyzed as a file in this batch gets.

### `filters/feTurbulence/stitchTiles=stitch.svg`

**What it tests.** `feTurbulence` with `baseFrequency=0.03` and `stitchTiles="stitch"`
— the Perlin-noise tile-seam-avoidance mode from filter-effects-1 §15.22 (adjusts the
effective frequency per-tile so the noise pattern repeats seamlessly at the primitive
subregion's edges, per the reference algorithm in the spec appendix / SVG 1.1 spec's
sample C code, which resvg and most SVG turbulence implementations port near-verbatim).

**Renders.** `ours.png` and `resvg.png` are near-pixel-identical (max channel diff 14
out of 255, mean 0.0067 — i.e., match to the eye, tiny floating-point rounding at
individual pixels). `chrome.png` shows a *different* specific noise pattern (same
overall "soft pastel blob" character and color palette, since it's driven by the same
fixed 256-entry Perlin permutation/gradient table from the spec, but the exact blob
shapes differ) — expected, since `stitchTiles`'s frequency-adjustment math is
sensitive to exact floating-point implementation and rounding choices that aren't
fully pinned down by the spec text, and Chromium/Skia's turbulence implementation is
independently written.

**Correct output + confidence: high (structurally), medium (bit-exactness).** The
overall visual character (frequency scale, color richness, absence of visible tile
seams — the entire point of `stitchTiles=stitch`) matches all three renders. Exact
noise-value agreement with resvg (max diff 14/255) is very strong given turbulence is
notoriously sensitive to arithmetic order; disagreement with Chromium's *exact* pattern
is expected and not evidence of a bug (this is precisely the kind of test the suite
marks UB because no two independent turbulence ports agree bit-for-bit).

**resvg verdict:** resvg correct, ours matches closely (not bit-exact, but far closer
than to Chromium, as expected for a resvg-ported implementation).

**Classification: (c)** — no fix needed; residual small diff from resvg is expected
floating-point noise in a chaotic function (Perlin noise amplifies tiny input
differences), not a structural bug. (Not (a): there's no concrete one-line diff to
point at — the remaining sub-visible mismatch would need a line-by-line audit of
`LeanSvg/Filter/Turbulence.lean`'s stitch-frequency-adjustment arithmetic against
resvg's `turbulence.rs` to fully close, which is possible but not clearly worth doing
for a 14/255-max, UB-labeled test.)

**Our status.** `LeanSvg/Filter/Turbulence.lean` implements `stitchTiles` (per DESIGN.md's
T65 changelog entry); the near-exact match to resvg (mean diff 0.0067) shows the
stitching frequency/wrap adjustment is implemented and working correctly.

### `filters/filter-functions/two-exact-urls.svg`

**What it tests.** SVG 2 / CSS Filter Effects `filter` property syntax:
`filter="url(#filter1) url(#filter1)"` — the *same* filter referenced twice in the
value list, which per the CSS filter-functions grammar should apply as a **chain**:
apply filter1, then apply filter1 again to that result (here, two sequential
`feGaussianBlur stdDeviation=4` passes, which should look visibly softer/wider-blurred
than a single pass — blurring twice is not the same as blurring once at the same
radius, since Gaussian blur convolution composes as `σ_total = sqrt(σ1² + σ2²)` ≈
5.66, not 4).

**Renders.** At a glance `ours.png`, `resvg.png`, and `chrome.png` all look like "one
blurred green square" and are easy to mistake for identical results at 200px. A
pixel-diff against a hand-built single-blur reference (`filter="url(#filter1)"`, one
pass only) shows all three actually **do** differ measurably from the single-pass
version at the blurred edge ring (max channel diff 170/255, concentrated in a ring
around the square's border) — confirming the filter *is* being chained/applied twice
in all three renderers, just subtly at this resolution. `suite.png` is the UB card.

**Correct output + confidence: high.** Chaining is implemented and produces the
expected wider/softer edge in all three renderers; ours matches resvg almost exactly
(max diff 4/255 between `ours.png` and `resvg.png` directly), and independently
differs from a single-pass blur by the same characteristic ring Chromium's double-pass
also produces. This is a real feature (SVG2 multi-value `filter` property / filter
function chains) working correctly, not a "UB, nobody agrees" case in practice — the
"(UB)" in the title more likely reflects that older SVG 1.1-only implementations (or
librsvg/QtSvg-era resvg, or batik) parse the property as a single `<FuncIRI>` and
either error or take only the first `url()`, which is why the suite doesn't score it
against the CSV's older-generation renderer set.

**resvg verdict:** resvg correct, ours matches.

**Classification: (c)** — no fix needed; already correctly implemented.

**Our status.** `LeanSvg/Filter.lean` around line 1011 and the surrounding
"`filter` value list" parsing (per its own doc comment: *"parse the `filter` value
list (`url(#id)` and the CSS filter [functions])"*, §3.11 pre-pass) already resolves
`filter="url(#a) url(#b)..."` into a sequence of filter applications rather than a
single lookup, and the render confirms two sequential Gaussian blur passes actually
run.
